# Aklatak — الأمان (SECURITY.md)

> النسخة 4.2. هدفنا **أعلى أمان عملي + أصغر سطح هجوم + اختبار مستمر**. لا يوجد نظام «آمن 100%».

## 1. البنية الأمنية
- **كل الحماية على السيرفر**: كل طلب يُفحص (هوية، صلاحية، مدخلات)، ولا ثقة بأي شيء يأتي من المتصفح أو التطبيق.
- **قاعدة البيانات** لا يصل إليها إلا السيرفر (مستخدم واحد عبر `DATABASE_URL`). الصلاحيات تُطبَّق في الكود ومغطّاة باختبارات. Row Level Security في Postgres مخطَّط كطبقة إضافية (انظر §9).
- **لا أسرار في الكود أو في GitHub**: كل الأسرار في متغيّرات البيئة على Render؛ `.env.example` بلا قيم.

## 2. الهوية والجلسات
| | |
|---|---|
| كلمات السر | `scrypt` مع ملح عشوائي؛ لا تُخزَّن ولا تُسجَّل أبداً |
| الجلسات | رمز عشوائي 256 بت؛ يُخزَّن **مُجزّأً (SHA-256)** في القاعدة؛ كوكي `HttpOnly` + `Secure` + `SameSite=Strict` |
| مدة الجلسة | الإدارة 12 ساعة، الطبّاخ/المطعم 60 يوماً؛ تغيير كلمة السر يُخرج من كل الأجهزة |
| تخمين كلمات السر | حدود محاولات لكل IP على دخول الإدارة والمشتركين؛ نفس الوقت للمستخدم الموجود وغير الموجود (لا كشف للحسابات) |
| **Passkey للإدارة** (اختياري، يفعّله المالك) | كلمة السر وحدها لا تكفي: بصمة/وجه عبر WebAuthn (ES256/RS256)، تحقّق من التحدّي والموقع وتوقيع الجهاز والعدّاد؛ رموز التحدّي تُستعمل مرة واحدة وتنتهي خلال 5 دقائق؛ لا يمكن تفعيله دون Passkey + رموز احتياطية (لا قفل للمالك خارج حسابه) |
| رموز احتياطية | 10 رموز، كل رمز مرة واحدة، مُجزّأة scrypt |
| سجلّ الدخول | كل محاولة (ناجحة/فاشلة، الطريقة، الجهاز) في `admin_logins`، ظاهرة في «أمان حسابي» |
| CSRF | `SameSite=Strict` + هيدر `X-Requested-With` + فحص `Origin` على كل طلب يغيّر بيانات |

## 3. الصلاحيات
- **الإدارة**: كل مسارات `/api/admin/*` تتطلّب جلسة إدارة؛ كل عملية حسّاسة تُسجَّل في `admin_actions`.
- **المشترك** (طبّاخ/مطعم): يرى ويعدّل **حسابه فقط** (`cook_id` من الجلسة، لا من الطلب). لا يستطيع تغيير اسمه أو رقمه أو حالته أو اشتراكه أو نوعه.
- **الشكاوى** للإدارة فقط؛ لا تظهر للمشترك ولا على صفحته.
- **الزبون** بلا حساب؛ التقييم يحتاج رمزاً سرياً يُعطى فقط بعد التواصل الفعلي.

## 4. المدخلات والمخرجات
- تحقّق من كل حقل (نوع، طول، قيم مسموحة)؛ استعلامات SQL **بمعاملات دائماً** (لا دمج نصوص).
- الصور: فحص **البايتات السحرية** (JPEG/PNG/WEBP) والحجم، أسماء عشوائية في التخزين، لا مسارات من المستخدم.
- روابط الإعلانات: `http(s)` أو مسار داخلي فقط (يمنع `javascript:`).
- الأسعار والمجموع في طلبات المطاعم **تُحسب على السيرفر** من المنيو، لا من المتصفح.
- رسائل الخطأ عامة؛ لا stack traces ولا أخطاء قاعدة البيانات للمستخدم.
- الحماية من XSS: كل نص يُعرض بعد تهريبه (escape)، وCSP صارمة (`default-src 'self'`).

## 5. الحدود ومنع الإساءة
حدود مستقلّة لـ: البحث، التواصل (WhatsApp)، الاشتراك، الدخول، الشكاوى، رسائل الدعم، الصور، البحث عن البلدات. مشتركة بين كل السيرفرات (Postgres أو Redis). عنوان IP الحقيقي يُقرأ من الوكيل الموثوق (لا يمكن تزويره).

## 6. ما لا نسجّله أبداً
كلمات السر، رموز الجلسات، المفاتيح، `DATABASE_URL`. السجلّات تحجب تلقائياً أي حقل اسمه password/secret/token/cookie/key.

## 7. نموذج التهديدات (مختصر)
| الأصل | التهديد | الحماية |
|---|---|---|
| حساب الإدارة | تخمين/سرقة جلسة | scrypt، حدود محاولات، HttpOnly/SameSite، رابط إدارة غير منشور، سجلّ عمليات |
| بيانات المشتركين | قراءة/تعديل حساب آخر (IDOR) | `cook_id` من الجلسة فقط + اختبارات |
| أرقام الهواتف | كشفها للزوار | لا تُرسل أبداً في واجهات العامة؛ رابط WhatsApp يُبنى على السيرفر |
| مواقع الناس | كشف العناوين | موقع الزبون يُقرَّب (~1 كم)؛ موقع المطبخ لا يظهر إلا كمسافة |
| الإعلانات/الصور | ملفات خبيثة | فحص البايتات، حجم، أنواع محدّدة |
| النصوص | XSS | تهريب كل النصوص + CSP |
| الخدمة | إغراق | حدود محاولات + (Cloudflare عند التكبير) |
| البيانات كلها | فقدان مزوّد | تصدير كامل + استرجاع مُختبَر (انظر MIGRATION.md) |

## 8. الاختبارات الأمنية
ضمن `npm test` (98 اختباراً، منها Passkey حقيقية بمفاتيح وتواقيع فعلية، ورفض التزوير وإعادة الاستعمال): رفض الوصول بلا جلسة، عدم كشف الأرقام والإحداثيات، عدم وصول المشترك للشكاوى، رفض CSRF، رفض روابط `javascript:`، رفض صور مزيّفة، حدود المحاولات، الموافقة الإلزامية على الشروط، عزل البلدان، التصدير والاسترجاع.

## 8.1 كشف أي تعديل على الكود (بصمة النسخة)
`/readyz` ولوحة الإدارة («أمان حسابي») تعرض **بصمة** محسوبة من كل ملفات المنصة. مع كل نسخة تُسلَّم البصمة المتوقعة؛ إن اختلفت بعد النشر فقد تغيّر شيء في الكود.

## 9. المتبقّي (بصراحة)
- **Passkey للإدارة**: جاهزة؛ تفعيلها قرار المالك من «أمان حسابي».
- **Row Level Security** في Postgres: الحماية الآن في السيرفر ومغطّاة بالاختبارات. RLS حقيقي يتطلّب تعريف المستخدم في كل اتصال بالقاعدة (`SET LOCAL app.cook_id`) وتعديل كل الاستعلامات، ولا يمكن اختباره هنا بلا Postgres. **الخطة**: (1) دور قاعدة بيانات للتطبيق غير مالك للجداول، (2) سياسات على `cooks`, `cook_photos`, `menu_items`, `support_messages`, `subscriptions` تسمح للمشترك بصفوفه فقط، (3) تجربة كاملة على فرع Neon منفصل، (4) ثم الإنتاج. نسخة مستقلة.
- **Git**: المشروع يُرفع كملف zip؛ يُنصح بمستودع Git حقيقي مع commits.
- **فحص الملفات من البرمجيات الخبيثة**: غير مطبّق (الصور فقط ومفحوصة بالنوع).
- **نسخ احتياطي تلقائي خارجي**: سكربت التصدير جاهز؛ جدولته اليومية تحتاج خدمة cron مدفوعة أو تشغيلاً يدوياً.

## 10. الإبلاغ عن ثغرة / حادث
1. أوقف الحساب أو الميزة المتأثرة من لوحة الإدارة (إخفاء/تعليق).
2. غيّر الأسرار المعنيّة على Render (`SESSION_SECRET` يُخرج الجميع؛ كلمة سر قاعدة البيانات من Neon).
3. صدّر نسخة من البيانات للتحقيق (`scripts/export-all.js`).
4. راجع `admin_actions` وسجلّات Render.
